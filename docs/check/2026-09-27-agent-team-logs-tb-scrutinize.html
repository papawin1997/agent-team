เจตนา

ให้ผู้ใช้หาสาเหตุที่ agent ล้มได้จากหน้า HTML เดียว โดยรวม agent-team.log กับ transcript ของ Agent SDK แล้วสรุปสาเหตุที่น่าจะเป็นไว้บนสุด

มีวิธีที่ง่ายกว่าไหม: มีบางส่วน สาเหตุหลักที่เจอจริง (529 และเน็ตหลุด) มาถึง runner อยู่แล้วเป็น message system/api_retry ที่มี type ชัดเจน ถ้า runner บันทึกข้อความนี้ลง log เองตั้งแต่แรก การวิเคราะห์สาเหตุหลักจะไม่ต้องพึ่งไฟล์ภายในของ ~/.claude เลย (ดู finding ข้อ 1) ส่วน transcript ยังมีประโยชน์สำหรับดูว่า agent เรียก tool อะไรไปบ้าง ตัว viewer จึงยังควรมีอยู่

ตรวจแล้วว่าทำงานจริง

  • node bin/agent-team.mjs logs C:/work/my/mail-sender ได้ logs.html ที่ __DEFAULT_RUN__ = 0 ซึ่งเป็นรอบที่ error เจอ 529 Overloaded ×30 และเชื่อมต่อ API ไม่ได้ ×10
  • รัน JS ของหน้าเว็บด้วย DOM shim กับไฟล์จริง: render, เปิดการ์ด (มี 4 step), เปิด <details> (สร้าง <pre> ตอนเปิดครั้งแรก) และสลับรอบ ทำงานได้โดยไม่มี error
  • npm test ผ่าน 754 เทสต์ และ npm run typecheck ไม่มี error
  • XSS: ทุกข้อความใส่ผ่าน textContent และ JSON escape < / U+2028 / U+2029 แล้ว
  • server: bind 127.0.0.1 และตรวจ Host header (ไม่สนตัวพิมพ์ใหญ่เล็ก)
  • agent ที่ล้มกลางคัน: parse-log.ts ปิด call เก่าเป็น exception เมื่อมี agent.start ใหม่ของ role เดียวกันเข้ามา และ findByTime ไม่เลือกไฟล์ที่ call อื่นใช้อยู่แล้ว
  • Windows: ใช้ explorer.exe แทน cmd เลยไม่มีปัญหา %VAR% ถูกแทนค่า

Findings

MAJORสาเหตุหลักอยู่ใน SDK stream อยู่แล้ว แต่ runner ไม่ได้บันทึกลง log ทำให้ viewer ต้องพึ่งไฟล์ภายในและการเดาจากช่วงเวลา

ทำไมสำคัญ
transcripts.ts อ่าน ~/.claude/projects/<dir>/<session>.jsonl ซึ่งเป็นรูปแบบไฟล์ภายในที่ไม่มีเอกสารรับรอง จะไม่มีข้อมูลให้อ่านเมื่อ:
  • ไฟล์ถูกลบ
  • เปิดดูจากคนละเครื่อง
  • CLAUDE_CONFIG_DIR ต่างกัน
  • path ยาวจนถูกตัดชื่อ
  • SDK เปลี่ยน format
กรณีเหล่านี้ทำให้กล่อง "สาเหตุที่น่าจะเป็น" ว่างเปล่า ทั้งที่ข้อมูลเคยผ่านมือ runner แล้ว นอกจากนี้ call ที่ไม่มี sessionId ยังต้องใช้ findByTime ซึ่งเป็นการเดาจากช่วงเวลา
หลักฐาน
sdk.d.ts:3383 SDKAPIRetryMessage { type:'system', subtype:'api_retry', attempt, error_status, error: 'overloaded'|'rate_limit'|'authentication_failed'|..., session_id } แต่ loop ใน src/runner.ts (บริเวณบรรทัด 199–230) จัดการแค่ init / assistant / result ส่วน session_id ก็ถูกเก็บไว้ในตัวแปรเท่านั้น จะถูกบันทึกลง log ก็ต่อเมื่อมี agent.result
แนวทางแก้ไข
  • ใน runner บันทึก agent.api_retry {role, attempt, status, error} และ agent.session {role, sessionId} ตอนที่เห็น session_id ครั้งแรก
  • diagnose.ts อ่านจาก event เหล่านี้ก่อน แล้วใช้ transcript เป็นข้อมูลเสริม
  • parse-log.ts เอา sessionId จาก agent.session มาใช้ ซึ่งจะทำให้ไม่ต้องพึ่ง findByTime แทบทั้งหมด
เป็นงานเล็กประมาณ 20 บรรทัด ทำเป็นงานถัดไปได้

MAJORcache ของ --live เก็บ JSON ดิบของ transcript ทุกไฟล์ไว้ตลอดอายุ server (transcripts.ts:41,57,68)

ทำไมสำคัญ
แก้ปัญหา CPU ได้ แต่ย้ายภาระไปที่ RAM แทน:
  • entry ที่เก็บเป็น object เต็ม รวม prompt ยาว ๆ และผล tool ที่ยังไม่ได้ตัด
  • findByTime ก็ parse และ cache ทุก .jsonl ในโฟลเดอร์ รวม session Claude Code ที่ผู้ใช้เปิดเองในโปรเจกต์นั้นด้วย
โปรเจกต์ใหญ่ที่เปิด --live ค้างไว้นาน ๆ จะใช้ RAM มากหลายเท่าของขนาดไฟล์
หลักฐาน
parseJsonl push { timestamp, entry } โดย entry คือ object ที่ได้จาก JSON.parse ทั้งก้อน จากนั้น loadEntries เก็บ array นี้ใน Map ที่ไม่มีการลบออกเลย
แนวทางแก้ไข
  • cache ผลที่แปลงแล้ว { time, steps: TranscriptStep[] } ซึ่งตัดข้อความไว้ที่ 2,000 ตัวอักษรแล้ว แทนการเก็บ entry ดิบ
  • สำหรับ findByTime ให้ cache แค่ timestamp แรกของแต่ละไฟล์
