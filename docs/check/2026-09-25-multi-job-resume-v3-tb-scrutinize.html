Scrutinize (รอบ 3): Multi-job resume — design spec

docs/superpowers/specs/2026-09-25-multi-job-resume-design.md @ 00dc06d · รีวิววันที่ 2026-09-25 · รอบก่อน: v1, v2

เจตนา

เป้าหมายเดิม: เก็บได้หลายงานใน jobs/<id>/ และมีเมนู r/d/n รอบนี้แก้ lock (unlockSync + SIGHUP, {pid, startedAt}, บอก path ให้ user ลบ lock เอง, unlink แล้วลอง wx ใหม่), ตัด fallback ของ migration ออก, แก้เงื่อนไข lastBuildAt และระบุ runTeam ให้ชัดขึ้น

มีวิธีง่ายกว่าไหม? ตอนนี้ spec ไม่มีส่วนที่เกินจำเป็นแล้ว ส่วนที่ซับซ้อนสุดคือ lock ซึ่งแต่ละข้อมีเหตุผลรองรับครบ ผมไม่เห็นทางที่เล็กกว่านี้ที่ยังกันการลบงานที่ process อื่นกำลังรันได้

ข้อจาก v2: แก้ครบไหม

  • v2#1 lock ค้าง ✅ มี unlockSync ด้วย rmSync ใช้ handler เดียวกันทั้ง SIGINT และ SIGHUP, เพิ่ม startedAt, เมนูบอก path ของ lock และมีเทสต์ handler
  • v2#2 migration ✅ เริ่มย้ายเฉพาะเมื่อมี state.json ที่ root และถ้าเจอ artifact ค้างให้ WARN โดยไม่ throw
  • v2#3 lastBuildAt ✅ เพิ่มเงื่อนไข rounds > 0 (แต่ยังมีช่องหนึ่งกรณี ดู nit #2)
  • v2#4 title ✅ ตั้ง title เฉพาะเมื่อ !pmSessionId และมีเทสต์แล้ว
  • v2#5 เทสต์ saves ✅ เขียนโค้ดตัวอย่างไว้ในหัวข้อ runTeam แล้ว
  • v2#6 race ✅ ใช้ mkdir แบบไม่ recursive, ถือว่า EPERM แปลว่า process ยังอยู่ และตอน lock ค้างใช้ unlink แล้วลอง wx ใหม่

Findings ใหม่

major

1. d<n> และการลบงานเปล่าอัตโนมัติ ตัดสินจาก lock ในข้อมูลที่อ่านมาตอนแสดงเมนู ถ้าอีก process lock งานนั้นหลังจากนั้น ก็ยังถูกลบได้

ทำไมสำคัญนี่คือกรณีที่ lock ถูกออกแบบมาป้องกันตั้งแต่ #3 และช่วงเวลาที่พลาดได้ไม่สั้น เพราะนับตั้งแต่แสดงเมนูจนถึงตอนที่ user ตอบ y ซึ่งอาจนานเป็นนาที
หลักฐานspec เขียนว่า "d<n> → ถ้างานถูก lock ให้บอก... ถ้าไม่ถูก lock ให้ถามยืนยัน ... แล้ว remove(id)" สถานะ lock มาจาก JobInfo.lock ที่ได้จาก list() ในขั้น 1 ลองไล่ตามลำดับนี้: terminal A เปิดเมนูไว้ → terminal B เลือก r1 (lock() สำเร็จ แล้วเริ่มรัน) → A พิมพ์ d1 แล้วตอบ y → remove ลบโฟลเดอร์ทั้งโฟลเดอร์ รวม lock ของ B ด้วย → พอ B save ครั้งถัดไป mkdir recursive (state.ts:64) จะสร้างโฟลเดอร์คืน แต่ artifacts หายไปแล้ว การลบงานเปล่าอัตโนมัติก็ใช้ข้อมูลจากตอนแสดงเมนูแบบเดียวกัน (แต่ช่วงเวลาสั้นกว่ามาก)
แนวทางแก้ไขให้ d เรียก lock(id) เองหลังจาก user ตอบ y ถ้า lock ไม่ได้ ให้บอกว่ากำลังรันอยู่แล้วแสดงเมนูใหม่ ถ้าได้ ค่อย remove(id) (lock จะถูกลบไปพร้อมโฟลเดอร์) การลบงานเปล่าให้ทำ "lock() แล้วค่อย remove()" แบบเดียวกัน แล้วเพิ่มเทสต์ "งานถูก lock หลังจากแสดงเมนูแล้ว เมื่อกด d → ถูกปฏิเสธ"
nit

2. เงื่อนไข rounds > 0 ไม่ได้กันการตั้ง lastBuildAt ตอนเข้า BUILD รอบที่สอง (หลังขอแก้ตอน DELIVER)

ทำไมสำคัญspec เขียนว่า "เพิ่งเข้า BUILD ยังไม่ตั้ง" แต่ข้อนี้จริงเฉพาะการเข้า BUILD ครั้งแรก เทสต์ที่วางแผนไว้จึงไม่ครอบกรณีนี้
หลักฐานinitProgress (domain.ts:59-60) เก็บ progress ของ task ที่ done และไม่ได้ changed ไว้เหมือนเดิม รวมถึง rounds ด้วย ดังนั้นตอน DELIVER→change→…→REVIEW confirm ระบบ save ในเฟส BUILD ขณะที่มี rounds > 0 อยู่แล้ว lastBuildAt จึงถูกตั้งทันทีก่อนมีการแก้โค้ด
แนวทางแก้ไขถ้าต้องการให้แม่นขึ้น ให้เช็กว่ามี task ที่ !p.done && p.rounds > 0 หรือ task ที่ done ใหม่ในรอบนี้ ถ้ายอมรับได้ ให้เพิ่มกรณีนี้ลงในย่อหน้า "ยอมรับว่ายังนับเกินจริงเล็กน้อย"
nit

3. --resume อาจเลือกงานที่ไม่ใช่ล่าสุดโดยไม่บอก user

ทำไมสำคัญถ้างานใหม่สุดถูก lock อยู่ ระบบจะข้ามไปทำงานที่เก่ากว่าโดยไม่บอก user อาจคิดว่ากำลังทำงานอีกงานอยู่
หลักฐานขั้น 3 ของ selectJob ไม่ได้ให้ io.say อะไรเลย ส่วน job.selected บันทึกลง log อย่างเดียว
แนวทางแก้ไขให้ io.say('ทำต่องาน "<ชื่อ>" (<id>)') ทุกครั้งที่ใช้ --resume
nit

4. เทสต์ signal handler ต้องส่งฟังก์ชัน exit เข้าไปแทนของจริง

ทำไมสำคัญถ้า handler เรียก process.exit ตรง ๆ เทสต์ vitest จะตายไปด้วย
หลักฐานhandler เดิมจบด้วย process.exit(130) (index.ts:52)
แนวทางแก้ไขระบุ signature เช่น makeInterruptHandler({ repo, getJobId, logger, abort, closeCli, exit })
nit

5. ถ้า 2 process เริ่มรันพร้อมกันตอนที่ยังมี legacy อยู่ process หนึ่งจะ error ตอน migration

ทำไมสำคัญมีโอกาสเกิดน้อย แต่ถ้าเกิด ผู้ใช้จะเห็น error "ย้ายไม่สำเร็จ" ทั้งที่อีก process ย้ายไปสำเร็จแล้ว
หลักฐานทั้ง 2 process เจอ state.json ที่ root พร้อมกัน พอฝั่งหนึ่ง rename ไปก่อน อีกฝั่งจะได้ ENOENT ซึ่งเข้าข้อ "ย้ายไฟล์ legacy ไม่สำเร็จ → throw"
แนวทางแก้ไขถ้า rename ได้ ENOENT ให้ถือว่าอีก process ย้ายไปแล้วและทำต่อได้เลย หรือเขียนไว้ใน "ไม่ทำ" ก็ได้

สิ่งที่ไล่ตรวจแล้ว (ยืนยันว่าถูก)

  • การกด Ctrl+C ใน readline (cli.ts rl.on('SIGINT') → process.emit('SIGINT')) ไปถึง handler เดียวกันที่เรียก unlockSync จึงปล่อย lock ทันก่อน exit
  • ถ้ากด Ctrl+C ระหว่าง selectJob หลังจาก create()/lock() แล้วแต่ยังไม่รู้ jobId lock จะค้างพร้อม pid ที่ตายไปแล้ว รอบถัดไปจะรู้ว่าค้างจาก ESRCH จึงยอมรับได้
  • ลำดับ "เขียน lock ก่อน state.json" ทำให้ list() ของอีก process ไม่เห็นงานที่กำลังสร้างอยู่ว่าเป็นงานเปล่าที่ไม่ได้ถูก lock
  • ถ้าย้าย legacy ล้มครึ่งทาง state.json ยังอยู่ที่ root → รอบถัดไปได้ id เดิมจาก mtime → ใช้โฟลเดอร์เดิมต่อ (ขั้น 2) ครบวงจร
  • โค้ดตัวอย่างของ runTeam ทำให้ orchestrator.test.ts:216-224 ผ่าน และเทสต์ resume ที่ตั้ง store.state ไว้ก่อนยังผ่านเหมือนเดิม

Verdict

fix-then-ship

เกือบพร้อมแล้ว เหลือแก้ #1 คือให้ d และการลบงานเปล่าอัตโนมัติเรียก lock() ก่อน remove() แก้ใน spec แค่ 1-2 บรรทัด แต่ถ้าไม่แก้ lock จะกันการลบงานที่อีก process กำลังรันไม่ได้ ซึ่งเป็นเหตุผลที่ใส่ lock เข้ามาตั้งแต่แรก ส่วน nit ที่เหลือจะแก้ตอน implement ก็ได้
