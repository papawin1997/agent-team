เจตนา

ให้งานเล็กเดินทางลัด: 1 task → worker → QA (≤2 รอบ) → ส่งมอบ ไม่ผ่าน Planning/REVIEW/Security ส่วนงานใหญ่หรืองานเสี่ยงยังเดินแบบเต็ม โดยให้ PM จัดระดับ และมีการเช็กคำเสี่ยงช่วยกันไว้อีกชั้น

มีวิธีที่ง่ายกว่าไหม:

  • ทางที่ง่ายสุด: มีแค่ --quick ที่ผู้ใช้สั่งเอง ไม่ต้องมี PM จัดระดับ ไม่ต้องจัดการกรณี PM เสนอใหม่กลางทาง และไม่ต้องมี baseDesign
  • ทำไมไม่เลือกทางนั้น: ผู้ใช้ตั้งใจเลือกให้ PM จัดระดับเพื่อให้ระบบตัดสินใจแทน และผลลัพธ์ก็ทำได้ตามนั้น
  • ต้นทุน: branch นี้เพิ่มโค้ดประมาณ 1,300 บรรทัด และ requirements.ts โตเป็น 240 บรรทัด มีฟังก์ชันตัดสินระดับ 5–6 ตัวพันกันอยู่ (decideLevel, confirmAsFull, acceptFull, clearStaleQuickDesign, restoreBaseDesign)
  • ควรทำก่อนโปรเจกต์ย่อย D: D (ยกระดับอัตโนมัติ + standard) จะมาเพิ่มในจุดเดียวกัน จึงควรแยกเรื่องระดับงานออกเป็น module ของตัวเอง (ดู nit ข้อสุดท้าย)

  • ยกระดับ quick → full ตอน escalate: build.ts:205-217 คืน base design ถ้ามี ถ้าไม่มีก็ล้างทิ้ง แล้วใส่บริบทลงใน designFeedback

Findings

MAJORการเช็ก SQL ไม่จับ SQL จริงที่พบบ่อย (src/risk.ts:53)

ทำไมสำคัญ
งาน quick ข้าม Security และการเช็กคำเสี่ยงเป็นชั้นเดียวที่ไม่ขึ้นกับการตัดสินของ PM ช่องว่างระหว่าง select/update กับ from/set ที่ยอมให้ไม่เกิน 8 ตัวอักษร ทำให้ query ที่มีรายชื่อคอลัมน์หรือชื่อตารางยาวหลุดทั้งหมด
หลักฐาน (probe ด้วย tsx บนโค้ดจริง)
[]      | SELECT id, name, email FROM users
[]      | update user_profiles set email
["sql"] | select * from orders
["sql"] | UPDATE users SET role = 1
regex ปัจจุบัน: \bselect\b[^\n]{0,8}?\bfrom\b และ \bupdate\b[^\n]{0,8}?\bset\b
แนวทางแก้ไข
เปลี่ยนจากจำกัดความยาวช่องว่าง มาใช้รูปแบบ token ของ SQL เช่น \bselect\s+(\*|[\w.]+(\s*,\s*[\w.]+)*)\s+from\s+[\w.]+ และ \bupdate\s+[\w.]+\s+set\s+[\w.]+\s*= ซึ่งยังไม่จับ "select a color from the palette" และ "update the header text and set color" แล้วเพิ่มตัวอย่างสองบรรทัดแรกของ probe เข้าเทสต์

NITหมวด delete ภาษาไทย (มี "ลบ" + "ทุก"/"ทั้งหมด" ตรงไหนก็ได้) จับงานแก้ไขทั่วไปเยอะ

ทำไมสำคัญ
คำเตือนขึ้นบ่อยเกินจนผู้ใช้เลิกสนใจ ซึ่งทำให้คำเตือนที่เป็นเรื่องจริงอ่อนค่าลง
หลักฐาน
["delete"] | แก้ปุ่มให้ทุกหน้าลบเงาออก
["delete"] | ลบ console.log ทุกไฟล์
["delete"] | ลบ todo ได้ทุกรายการ
แนวทางแก้ไข
เลือกได้สองแบบ:
  • ให้ "ลบ" ต้องอยู่ใกล้คำที่หมายถึงข้อมูล เช่น ข้อมูล, ผู้ใช้, ลูกค้า, บัญชี, ตาราง, ฐานข้อมูล
  • ให้ "ทั้งหมด"/"ทุก" ต้องตามหลัง "ลบ" ภายในประมาณ 20 ตัวอักษร
แล้วเพิ่มสามบรรทัดใน probe เป็นเทสต์กรณีที่ต้องไม่ถูกจับ

NITdeps.levelHintSent เก็บ state ไว้ใน object ของ dependency (requirements.ts:42-44)

ทำไมสำคัญ
Deps คือของที่ส่งเข้ามาจากข้างนอก การเก็บ flag ไว้ในนั้นทำให้พฤติกรรมขึ้นกับว่า object ถูกใช้ซ้ำหรือเปล่า เช่นเทสต์ที่ใช้ deps ชุดเดียวหลายครั้ง หรือ runner แบบ headless ในโปรเจกต์ย่อย B ที่อาจรันหลายงานต่อ process
หลักฐาน
if (deps.levelPreference && !deps.levelHintSent) { … deps.levelHintSent = true; }
แนวทางแก้ไข
ให้ runTeam ถือ flag นี้ไว้เป็นตัวแปรของการรันแต่ละครั้ง แล้วส่งเข้า runRequirements หรือเก็บไว้ใน state ในฐานะ "ส่ง hint แล้วในรอบรันนี้"

NITคำเสี่ยงจากข้อความผู้ใช้สะสมเฉพาะรอบรันปัจจุบัน และไม่ลดลงเมื่อผู้ใช้ถอนคำขอ

ทำไมสำคัญ
  • ถ้า resume งานกลางการคุยกับ PM ข้อความเสี่ยงที่พิมพ์ในรอบก่อนจะไม่ถูกนับ
  • ถ้าผู้ใช้พิมพ์ "ไม่เอา login แล้ว" ก็ยังถูกเตือนเรื่อง auth ต่อ
ทั้งสองกรณีเป็นแค่คำเตือน ผลกระทบจึงต่ำ
หลักฐาน
userRisk เป็นตัวแปรใน runRequirements (:22) ที่เริ่มว่างทุกครั้งที่เรียก และมีแต่ mergeRiskFlags ไม่มีการลบ
แนวทางแก้ไข
บันทึกข้อจำกัดนี้ไว้ใน README (คำเตือนเป็นแบบ best-effort อยู่แล้ว) หรือเก็บ userRisk ลง state เพื่อให้คงอยู่หลัง resume

NITแยก logic ตัดสินระดับงานออกจาก requirements.ts ก่อนเริ่มโปรเจกต์ย่อย D

ทำไมสำคัญ
D จะเพิ่มระดับ standard และการยกระดับอัตโนมัติในจุดเดียวกัน ถ้าไม่แยกตอนนี้ ไฟล์ phase จะกลายเป็นที่รวมกฎของระดับงานทั้งหมด
หลักฐาน
requirements.ts 240 บรรทัด ในนั้นมีฟังก์ชันเรื่องระดับ 5 ตัว ส่วน build.ts ก็มี logic ยกระดับ/คืน base design แยกอยู่อีกชุด
แนวทางแก้ไข
สร้าง src/level/ หรือขยาย src/level.ts ให้รวม decideLevel, acceptQuick, acceptFull, escalateToFull และ restoreBaseDesign ไว้ด้วยกัน แล้วให้ phase เรียกใช้ ไม่ต้องเปลี่ยนพฤติกรรม

Verdict

fix-then-ship

เหตุผลหลัก: flow ของ quick, การยกระดับ, baseDesign และการ resume ไล่แล้วถูกต้อง แต่การเช็ก SQL ซึ่งเป็นชั้นป้องกันเดียวที่ไม่ขึ้นกับ PM สำหรับงานที่ข้าม Security ยังหลุด query จริงที่พบบ่อย แก้ regex พร้อมเทสต์ได้ในไม่กี่บรรทัด ส่วน nit ทำพร้อมกันหรือเก็บไปทำก่อนเริ่ม D ก็ได้
