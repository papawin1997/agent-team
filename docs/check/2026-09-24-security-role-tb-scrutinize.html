เจตนา

เป้าหมาย (สรุปด้วยคำของผม): เพิ่ม agent อ่านอย่างเดียวอีกหนึ่งตัวมาเป็น "ตาคู่ที่สอง" ด้านความปลอดภัย — ทักท้วง design ก่อนลงมือ แล้วยับยั้งไม่ให้ task ที่ QA ปล่อยผ่านกลายเป็น done ถ้ามีช่องโหว่

มีวิธีเล็กกว่านี้ไหม — มี และควรพิจารณาก่อนขยายเพิ่ม: ในฝั่ง BUILD ตัว security ได้ input ชุดเดียวกับ QA เป๊ะ ๆ (task/result/design/requirements — src/prompts.ts:109-135), มีเครื่องมือเป็น subset ของ QA และสุดท้าย issue ก็ถูกยัดกลับเข้า QAReport เดิมอยู่ดี (src/phases/build.ts:78) ผลลัพธ์ที่ผู้ใช้เห็นจึงเหมือน QA ทุกประการ สิ่งเดียวกันได้จากการเพิ่ม 'security' เข้า QACheckSchema.name + ย่อหน้า OWASP ใน QA_PROMPT — ไม่ต้องมี role ใหม่, ไม่ต้องมี schema ใหม่, ไม่ต้องมี merge logic, และประหยัด Sonnet 1 call ต่อรอบ build ทุกรอบที่ QA ผ่าน ส่วนฝั่ง DESIGN ก็ให้ Planning เติม securityNotes เองได้ (field มีใน DesignSchema อยู่แล้ว) ซึ่งจะตัดปัญหา blocker ข้อ B-1 ด้านล่างทิ้งทั้งก้อน

เหตุผลเดียวที่แยก role คุ้ม คือ "ความเป็นอิสระของบริบท" — แต่โค้ดที่ merge มาไม่ได้ใช้ประโยชน์ข้อนั้นเลย (คนละ session อยู่แล้ว แต่ข้อมูลนำเข้าเหมือนกัน และ verdict ถูกยุบรวมทันที) ถ้าจะเก็บ role ไว้ ควรเก็บเพราะอยากให้มัน "ตรวจได้หลายไฟล์ข้าม task" ซึ่งตอนนี้มันทำไม่ได้

N-4 — guard เป็น default-allow สำหรับ tool ที่ไม่รู้จัก การันตี read-only จึงพิงอยู่บน SDK option tools เป็นหลัก ไม่ใช่ guard (src/guard.ts:95-108)

ทำไมสำคัญ ไม่ใช่ช่องโหว่ที่ใช้งานได้ในคอนฟิกปัจจุบัน แต่เป็น defense-in-depth ที่หายไป ถ้าวันหนึ่งมีใครเพิ่ม tool เข้า READ_TOOLS ของ config หรือ SDK เพิ่ม built-in ใหม่ guard จะไม่ทักอะไรเลยสำหรับ role ที่ประกาศว่า read-only
หลักฐาน (เส้นทางที่ไล่ — ข้อสรุป: read-only ปัจจุบัน "จริง") ผมไล่ 3 ชั้นแล้วยืนยันว่า security เขียนไฟล์/รันคำสั่งไม่ได้จริง:
  • ชั้น 1 — config.ts:67: tools: READ_TOOLS และ allowedTools: READ_TOOLS = ['Read','Glob','Grep'] เท่านั้น; RoleOverrideSchema (config.ts:71-78) ไม่ยอมให้ override tools/allowedTools ผ่านไฟล์ config และ .strict() จะ throw (เทส tests/config.test.ts ยืนยัน). Options.tools ของ SDK (sdk.d.ts:1568) เป็น allowlist จริง
  • ชั้น 2 — options.ts:29: permissionMode: 'dontAsk' = ปฏิเสธถ้าไม่ pre-approved + strictMcpConfig: true (options.ts:36) และไม่มี mcpServers
  • ชั้น 3 — guard.ts:95-98: readOnlyRole รวม 'security' แล้ว deny ทั้ง Write/Edit/NotebookEdit และ Bash; createGuardHook fail-closed ที่ 149-152
ส่วนที่เหลือเป็นช่องว่างเชิงโครงสร้าง: checkToolUse ปิดท้ายด้วย return OK (guard.ts:108) สำหรับทุก tool ที่ไม่อยู่ในสามหมวด และ settingSources: ['project'] (options.ts:30) ยังโหลด .claude/settings.json ของโปรเจกต์เป้าหมาย (README บรรทัด 76 เตือนไว้แล้ว)
แนวทางแก้ไข กลับด้าน logic สำหรับ role read-only: อนุญาตเฉพาะ tool ที่อยู่ใน READ_TOOLS แล้ว deny ที่เหลือทั้งหมด (แก้ guard.ts:95-98 เป็น ~3 บรรทัด) และ/หรือใส่ disallowedTools ใน buildQueryOptions

สิ่งที่ตรวจแล้วและผ่าน

  • Read-only ของ security: ไล่ครบ 3 ชั้นตาม N-4 — ยืนยันว่าเขียนไฟล์/รัน Bash ไม่ได้จริง และ override ผ่าน config ก็ยกระดับสิทธิ์ไม่ได้
  • Merge issues + บังคับ FAIL ในเคสปกติ: build.ts:75-80 → isPass(mergedReport) (128) คืน false ถูกต้อง เพราะทั้ง verdict และ severity; progress.rounds เพิ่ม 1 ครั้งต่อรอบพอดี (124) ไม่มีการนับซ้ำหรือนับข้าม ทั้งในเส้นทาง security PASS, security FAIL และ limit-hit
  • isSecurityPass (domain.ts:46-48): PASS+blocker → false ถูกต้อง, PASS+minor เท่านั้น → true ถูกต้อง
  • ลำดับ phase และการ save: store.save ถูกเรียกทุกรอบ (build.ts:147, 150) ทำให้ --resume ใช้ได้ตามที่ README อ้าง
  • README: บรรทัด 20-27, 49-52, 62-63, 71 ตรงกับโค้ดจริงทั้งหมด ยกเว้นบรรทัด 40 (ดู N-1) และ "advisory" ที่บรรทัด 21 ซึ่งถูกต้องแต่ผู้ใช้ไม่เคยเห็น (ดู B-1)
  • สภาพปัจจุบัน: npm test 457 ผ่านทั้งหมด, npm run typecheck สะอาด
