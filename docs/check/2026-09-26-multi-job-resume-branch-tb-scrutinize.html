Findings

MAJOR fs.link ใน tryCreateLock ทำให้ทั้งโปรแกรมใช้ไม่ได้บนไดรฟ์ที่ไม่รองรับ hard link (src/jobs.ts:260-274)

ทำไมสำคัญ
commit e5f1453 เปลี่ยนจาก writeFile(wx) ที่ใช้ได้ทุก filesystem มาใช้ fsp.link ถ้าโปรเจกต์อยู่บน exFAT/FAT32 (USB drive), network share บางแบบ หรือ mount ของ Docker/WSL link จะ throw error ที่ไม่ใช่ EEXIST/ENOENT ผลคือ create() และ lock() throw ทุกครั้ง และเริ่มงานไม่ได้เลย ทั้งที่เดิมใช้ได้ การแก้ race ที่แทบไม่เกิดจึงไปสร้างความเสี่ยงที่ทำให้โปรแกรมใช้ไม่ได้ทั้งหมด
หลักฐาน
selectJob → repo.create() → lock(id) → tryCreateLock → fsp.link throw (เช่น EPERM/ENOTSUP) → ไม่เข้าเงื่อนไข EEXIST||ENOENT → throw e → index.ts catch → "หยุดเพราะ error" ยังไม่ได้ลองบนไดรฟ์จริง แต่ exFAT/FAT ไม่มี hard link อยู่แล้วโดยโครงสร้าง (สถานะ: PLAUSIBLE)
แนวทางแก้ไข
ทางที่ง่ายกว่าคือกลับไปใช้ wx แล้วแก้ที่ฝั่งคนอ่านแทน ใน lock() ถ้า readLock คืน undefined (ไฟล์ว่างหรือพัง) แต่ mtime ของไฟล์ยังไม่เกิน ~5 วินาที ให้คืน false ไปก่อน ไม่ต้องถือว่าค้าง วิธีนี้ปิด race ข้อ 2 ได้เหมือนกัน ใช้ได้ทุก filesystem และไม่ต้องมีไฟล์ชั่วคราว ถ้าอยากเก็บ link ไว้ ต้องมี fallback เป็น wx เมื่อ link ล้มด้วย error อื่นที่ไม่ใช่ EEXIST/ENOENT

MAJOR ระบบให้รัน 2 งานที่ต่างกันพร้อมกันบนโค้ดชุดเดียวกันได้โดยไม่เตือน (src/job-menu.ts:84-99)

ทำไมสำคัญ
lock กันได้แค่ "งานเดียวกัน" ถ้าหน้าต่าง A กำลัง BUILD งาน X อยู่ หน้าต่าง B กด n หรือ r งาน Y ได้ทันที worker ของทั้งสองงานจะแก้ไฟล์ใน working tree เดียวกันพร้อมกัน QA ของงานหนึ่งจะเห็นโค้ดที่อีกงานแก้ค้างครึ่งทาง และ codeChangedWarning เตือนได้แค่ หลังจากเกิดไปแล้ว สเปกไม่ได้ระบุว่าตั้งใจให้เป็นแบบนี้หรือเป็น out of scope
หลักฐาน
เมนูโชว์ "(กำลังรันอยู่ pid …)" ของงาน X แต่ menu() เช็ก job.lock เฉพาะงานที่เลือก ส่วน n → repo.create() ไม่ได้ดู lock ของงานอื่นเลย --resume (resumeLatest) ก็ข้ามงานที่ถูก lock แล้วไปหยิบงานค้างอื่นมารันต่อเงียบ ๆ
แนวทางแก้ไข
ต้องตัดสินใจก่อนว่าตั้งใจไหม ถ้าไม่ตั้งใจ แก้ที่เล็กที่สุดคือ ก่อน n/r/--resume ถ้าใน all มีงานอื่นที่มี live lock ให้ขึ้นเตือน "มีงาน … กำลังรันในโปรเจกต์นี้ แก้โค้ดชนกันได้" แล้วถาม y/n (ส่วน --resume ให้ error) ถ้าตั้งใจ ให้เขียนใน README และสเปกว่าไม่รองรับการรันพร้อมกัน

NIT กด Ctrl+C ระหว่าง create() ทิ้งโฟลเดอร์ที่ไม่มี state ไว้ถาวร (src/jobs.ts:108-129, src/index.ts:61-62)

ทำไมสำคัญ
ถ้าหยุดหลัง mkdir+lock แต่ก่อน save จะเหลือโฟลเดอร์ที่มีแค่ run.lock ทุกครั้งที่รันหลังจากนั้น list() จะ log job.missing_state และไม่มีโค้ดส่วนไหนเก็บกวาดโฟลเดอร์นี้ให้ ช่วงเวลาที่เกิดได้สั้นมาก (ระดับ ms)
หลักฐาน
ตอนนั้น jobId ใน index.ts ยังเป็น undefined (ตั้งหลัง selectJob คืนค่า) handler จึงไม่ unlock ส่วน list() เจอ state เป็น undefined ก็ continue ข้ามไป removeEmptyJobs จึงไม่เคยเห็นงานนี้
แนวทางแก้ไข
ใน list() ถ้าไม่มี state.json และไม่มี live lock ให้ removeQuietly ทิ้ง (โฟลเดอร์ที่ create() ทำไม่เสร็จ) แทนการ WARN อย่างเดียว

ทำไมสำคัญ

แนวทางแก้ไข
ถ้าใช้วิธี mtime-grace ตาม finding #1 จะเทสต์แบบได้ผลแน่นอนได้: เขียน run.lock ว่างที่ mtime = ตอนนี้ แล้วเช็กว่า lock() ของอีก pid ได้ false และถ้า mtime เก่ากว่า grace แล้วได้ true ส่วนเทสต์ loop 50 รอบให้ลบทิ้ง

NIT ชื่อไฟล์ชั่วคราว run.lock.<pid>.tmp ชนกันได้ถ้า process เดียวกัน lock งานเดียวกันพร้อมกัน (src/jobs.ts:262)
