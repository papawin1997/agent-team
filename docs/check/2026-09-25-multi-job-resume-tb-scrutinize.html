Scrutinize: Multi-job resume — design spec

docs/superpowers/specs/2026-09-25-multi-job-resume-design.md · branch feat/multi-job-resume · รีวิววันที่ 2026-09-25

เจตนา

ให้ 1 โปรเจกต์เก็บงานค้างได้หลายงาน (โฟลเดอร์ jobs/<id>/) และตอนเริ่มรันมีเมนูให้เลือก ทำต่อ / ลบ / เริ่มใหม่ แทนที่จะ error แล้วบอกให้ใช้ --resume

มีวิธีง่ายกว่าไหม? ภาพรวมเลือกทางถูกแล้ว: StateStore interface ไม่เปลี่ยน และ phase ไม่ต้องแก้ ซึ่งผมไล่โค้ดแล้วยืนยันว่าจริง (phase ใช้แค่ store.save/saveArtifact ส่วน guard.ts:27 ก็กัน .agent-team ทั้งโฟลเดอร์อยู่แล้ว) แต่ยังตัดออกได้อีก 2 อย่าง:

  • createdAt ไม่มีใครใช้ เพราะเรียงและเตือนด้วย updatedAt และ jobId ก็เป็นเวลาสร้างอยู่แล้ว ตัดทิ้งได้
  • ตัด flag resume ที่ส่งจาก selectJob ไป runTeam เปลี่ยนเป็น runTeam ใช้ load() ?? newState() อย่างเดียว เพราะ selectJob ยืนยันไว้แล้วว่างานที่เลือกมี state จริง ถ้าคง flag ไว้จะชนกับเทสต์เดิม (ดู major #2)

Findings

major

1. "งานเปล่า" จะเต็มเมนู ทำให้ต้องตั้งชื่อว่า "(ยังคุย requirements ไม่เสร็จ)" ซ้ำกันหลายงาน และทำให้ทุกงานขึ้นคำเตือน

ทำไมสำคัญข้อตัดสินใจ #4 บอกว่าจะใช้สรุปที่ละเอียดพอแทนการพิมพ์ถาม PM แต่งานในเฟส REQUIREMENTS จะดูไม่ออกว่าเป็นงานไหน และ --resume อาจไปหยิบงานเปล่าแทนงานจริง
หลักฐาน
  • requirements.ts:12 ข้อความแรกที่ user พิมพ์ได้มาจาก askNonEmpty ซึ่งไม่ถูกเก็บลง state และบรรทัด 16 ตั้ง pendingPrompt = undefined ก่อน save ที่บรรทัด 21 เลยไม่เหลืออะไรให้ใช้เป็นชื่อ ผลคือ fallback "ใช้ pendingPrompt" แทบไม่เคยได้ใช้ งานที่ค้างใน REQUIREMENTS จึงได้ชื่อ "(ยังคุย requirements ไม่เสร็จ)" แทบทุกงาน
  • กด n → create() เขียน state ทันที ถ้าผู้ใช้ Ctrl+C ตรงคำถามแรก งานเปล่านี้จะค้างในเมนูตลอด เพราะ updatedAt ใหม่สุด → ทุกงานเก่าขึ้น "⚠ มีงานอื่นรันหลังจากงานนี้" และ --resume ก็จะเลือกงานเปล่านี้
แนวทางแก้ไข(ก) เพิ่ม State.title?: string ตั้งค่าจากข้อความแรกที่ user พิมพ์ใน runRequirements แล้วใช้ลำดับ requirements.goal → title เป็นชื่องาน (ข) ถือว่างานที่ไม่มี pmSessionId / title / requirements เป็น "งานเปล่า" ไม่แสดงในเมนู ไม่นับตอนคำนวณคำเตือน และไม่ให้ --resume เลือก (ลบทิ้งอัตโนมัติด้วยก็ได้) แล้วเขียนเทสต์ครอบกรณีนี้
major

2. ข้อกำหนดของ runTeam(resume:false) ขัดกับเทสต์เดิม และ createdAt อาจถูกเขียนทับ

ทำไมสำคัญผู้ implement ต้องเดาเองว่าควรทำอะไร ถ้าเดาทางหนึ่ง เทสต์เดิมจะพัง ถ้าเดาอีกทาง ข้อมูลที่ spec บอกให้บันทึกจะหาย
หลักฐานspec เขียนว่า "resume:false → ใช้ state ที่ create() เขียนไว้" แต่ tests/orchestrator.test.ts:176-213 (it.each DONE/ABORTED) ใส่ state ที่จบแล้วแล้วเรียก resume:false โดยคาดว่าได้งานใหม่ ถ้าใช้ state ที่โหลดมา loop ใน orchestrator.ts:29 จะไม่ทำงานเลยเพราะ phase เป็น DONE อยู่แล้ว เทสต์นี้จะพัง ทั้งที่ spec บอกให้แก้แค่เทสต์ที่บรรทัด 170 ส่วนอีกทาง ถ้าคงโค้ดเดิม state = newState() ไว้ createdAt ที่ create() เขียนไว้ก็จะหาย
แนวทางแก้ไขเขียนให้ชัดใน spec ว่า runTeam ใช้ existing ?? newState() (ถ้า resume และไม่มี state ก็ throw เหมือนเดิม) แล้วลบ it.each DONE/ABORTED พร้อมเทสต์ที่บรรทัด 170 เพราะงานใหม่จะอยู่ในโฟลเดอร์ใหม่เสมอ จึงไม่มีกรณีเริ่มงานใหม่ทับ state เก่าอีกแล้ว และตัด createdAt ทิ้ง หรือถ้าจะเก็บไว้ ให้ save ตั้ง createdAt ??= now
major

3. ไม่มี lock: เปิด 2 terminal แล้วจะ resume หรือลบงานที่อีก process กำลังรันอยู่ได้

ทำไมสำคัญของเดิมมีตัวกันโดยบังเอิญ คือ orchestrator.ts:17-21 error ถ้ารันซ้ำโดยไม่ใส่ --resume spec ลบตัวกันนี้ออก และเมนูใหม่ยังชวนให้เปิดหลายงาน ถ้ากด d ใส่งานที่ยังรันอยู่ พอ process นั้นเรียก save ครั้งถัดไป state.ts:64 จะใช้ mkdir recursive สร้างโฟลเดอร์คืนมา แต่มีแค่ state.json ส่วน artifacts หายไปแล้ว ถ้ากด r จะมี 2 process เขียน state เดียวกันทับกันไปมา
หลักฐานใน spec ไม่มี lock หรือ pid ตรงไหนเลย และหัวข้อ "ไม่ทำ" ก็ไม่ได้ระบุเรื่องนี้
แนวทางแก้ไขทางที่เล็กที่สุด: ตอนเลือกงาน ให้เขียน jobs/<id>/run.lock (เก็บ pid) และลบตอนจบหรือตอน SIGINT ในเมนูให้แสดง "(กำลังรันอยู่ pid N)" แล้วไม่ยอมให้ r/d งานนั้น ถ้า pid ตายไปแล้ว (เช็คด้วย process.kill(pid,0)) ถือว่า lock ค้าง ใช้ต่อได้ หรืออย่างน้อยเขียนไว้ใน "ไม่ทำ" ให้ชัด
major

4. ถ้าย้าย legacy ล้มกลางทาง แล้วรันใหม่จะไม่ได้ย้ายต่อ ไฟล์จะหายหรือแยกกันอยู่

ทำไมสำคัญspec บอกว่า "throw เพื่อไม่ให้ state ปนกัน" แต่ไม่ได้กำหนดลำดับการย้าย จึงรันซ้ำให้ได้ผลเดิม (idempotent) ไม่ได้
หลักฐานสิ่งที่จะเริ่มย้ายคือ "มี .agent-team/state.json อยู่" (ข้อ 1-2) มีสองแบบ: ถ้าย้าย state.json ก่อน แล้วไปล้มตอนย้าย reports/ รอบหน้าจะไม่มี legacy ให้เจอแล้ว reports/ จะค้างอยู่ที่ root ตลอด ถ้าย้าย artifacts ก่อนแล้วไปล้ม รอบหน้าได้ id เดิม (เพราะ mtime ไม่เปลี่ยน) แต่โฟลเดอร์นั้นมีอยู่แล้ว กฎกันชื่อซ้ำจะต่อท้าย -2 ทำให้ artifacts ถูกแยกไปอยู่คนละโฟลเดอร์ และ list() จะเตือน WARN "ไม่มี state.json" ทุกครั้ง
แนวทางแก้ไขระบุใน spec: (1) ถ้าโฟลเดอร์ jobs/<id> มีอยู่แล้วแต่ไม่มี state.json ให้ใช้โฟลเดอร์นั้นต่อ ไม่ต่อท้าย suffix (2) ย้าย artifacts ก่อน และย้าย state.json เป็นอย่างสุดท้าย แล้วเพิ่มเทสต์ "ล้มครึ่งทางแล้วรันใหม่ได้ผลครบ"
major

5. คำเตือน "โค้ดอาจเปลี่ยน" จะขึ้นแทบทุกครั้งจนไม่มีใครสนใจ

ทำไมสำคัญคำเตือนที่ขึ้นตลอดเวลาจะไม่มีประโยชน์ เพราะผู้ใช้จะชินจนไม่อ่าน
หลักฐานupdatedAt เปลี่ยนทุกครั้งที่ save ทุกเฟส รวมถึงตอนคุยกับ PM (requirements.ts:21, io-util.ts:39) แต่โค้ดจะถูกแก้จริงแค่ในเฟส BUILD ดังนั้นถ้าเปิดงานใหม่แล้วคุย requirements แค่ประโยคเดียว งานเก่าทุกงานก็จะขึ้นคำเตือนแล้ว
แนวทางแก้ไขนับเฉพาะงานอื่นที่ผ่านเฟส BUILD มาแล้ว เช่นมี progress[*].rounds > 0 หรือเพิ่ม lastBuildAt ใน build.ts ตอน save รอบ QA แล้วเทียบกับ updatedAt ของงาน X ใช้แค่ข้อมูลที่มีอยู่แล้ว ไม่ต้องพึ่ง git
nit

6. หน้ายืนยันลบบอกว่า "พิมพ์คำถามถึง PM ได้" ซึ่งขัดกับข้อตัดสินใจ #4

ทำไมสำคัญUX ขัดกันเอง ผู้ใช้พิมพ์คำถามลงไปจะได้แค่ "กรุณาพิมพ์หมายเลข..."
หลักฐานCliIO.choose → chooseOrText (cli.ts:78) ต่อท้ายข้อความ "หรือพิมพ์คำถาม/ความเห็นถึง PM ก่อนตัดสินใจก็ได้" ให้เสมอ
แนวทางแก้ไขถามยืนยันด้วย io.ask ตรง ๆ แล้วรับ y/yes/n/no เอง ทำแบบเดียวกับเมนู
nit

7. ถ้าใส่ jobId ใน run.start ต้องย้ายลำดับโค้ด และข้อความ SIGINT ระหว่างที่อยู่ในเมนูจะอ้างถึงงานที่ยังไม่มี

ทำไมสำคัญถ้าย้าย run.start ไปไว้หลังเมนู log ของการเลือกในเมนู (LoggingIO) จะมาก่อน run.start ทำให้อ่านลำดับใน log ยาก
หลักฐานindex.ts:25 log run.start ก่อนสร้าง store และ SIGINT handler (index.ts:47) ถูกลงทะเบียนก่อนจะรู้ jobId
แนวทางแก้ไขคง run.start ไว้ที่เดิม แล้วเพิ่ม event job.selected {jobId, resume} หลัง selectJob ข้อความ SIGINT ให้ใช้ jobId แบบ optional
nit

8. ข้อความ error ใน orchestrator ยังอ้าง path เก่า

ทำไมสำคัญข้อความจะบอก path ที่ไม่มีแล้ว ทำให้ผู้ใช้หาไฟล์ผิดที่
หลักฐานorchestrator.ts:14 'ไม่พบ state ให้ resume (.agent-team/state.json)' และ README บรรทัด 30-32
แนวทางแก้ไขเพิ่มลงรายการ "การเปลี่ยนแปลงอื่น"

สิ่งที่ไล่ตรวจแล้ว (ยืนยันว่าถูก)

  • "phase ไม่ต้องแก้" จริง: grep แล้วพบว่า src/phases/* ใช้แค่ store.save / store.saveArtifact (ชื่อไฟล์แบบ relative) ไม่มีที่ไหนใช้ path .agent-team ตรง ๆ
  • guard PROTECTED_DIRS (guard.ts:27) ยังกัน .agent-team/jobs/ ได้ เพราะกันไว้ที่ระดับโฟลเดอร์แม่ ส่วน prompts.ts:61 ก็ยังถูกต้อง
  • ScriptedIO (tests/helpers/fakes.ts:36) มี ask/choose ครบแล้ว จึงเทสต์เมนูได้ตามแผน
  • FileLogger ไฟล์เดียวใช้ร่วมกันทุกงานได้ เพราะเขียนแบบ append sync
  • ความหมายใหม่ของ --resume: ถ้ามีแต่งานที่ DONE จะ throw เป็นพฤติกรรมที่เปลี่ยนไปจากเดิม (เดิมจะจบเงียบ ๆ) ถือว่ายอมรับได้ แต่ควรเขียนไว้ใน README

Verdict

fix-then-ship

โครงหลักถูกต้องแล้ว (interface เดิม, phase ไม่ต้องแก้) แต่ยังต้องแก้เรื่องชื่องานและงานเปล่า (#1) กับข้อกำหนด runTeam ที่ขัดกับเทสต์เดิม (#2) ใน spec ก่อน ไม่อย่างนั้นเมนูจะไม่ช่วยให้เลือกงานได้จริง และผู้ implement ต้องเดาเอง
