Scrutinize (รอบ 2): Multi-job resume — design spec

docs/superpowers/specs/2026-09-25-multi-job-resume-design.md @ 47ff71f · รีวิววันที่ 2026-09-25 · รอบก่อน: 2026-09-25-multi-job-resume-tb-scrutinize.html

เจตนา

เหมือนรอบแรก คือเก็บงานได้หลายงานใน jobs/<id>/ และมีเมนูให้เลือก r/d/n รอบนี้เพิ่ม title, lastBuildAt, lock ด้วย pid, การย้ายไฟล์ legacy ที่รันซ้ำได้ผลเดิม และเปลี่ยน runTeam(deps) ให้ไม่มี flag

มีวิธีง่ายกว่าไหม? lock เป็นส่วนที่ซับซ้อนที่สุดที่เพิ่มเข้ามา แต่ยังคุ้ม เพราะถ้าไม่มี lock การกด d จะลบงานที่ process อื่นกำลังรันได้ ส่วนที่ตัดได้คือ fallback ในขั้น 1 ของ migration (ดู #2) เพราะเป็นโค้ดที่ไม่มีวันถูกเรียก

findings รอบแรก: แก้ครบไหม

  • #1 ชื่องาน/งานเปล่า ✅ มี title และนิยาม "งานเปล่า" ที่ลบอัตโนมัติ กันลบงานที่ process อื่นเพิ่งสร้างด้วย lock ที่เขียนก่อน state.json
  • #2 runTeam ✅ ไม่มี flag แล้ว และระบุเทสต์ที่ต้องลบไว้ครบ 3 ตัว (เหลือเรื่องเล็ก ดู nit #5)
  • #3 lock ✅ แต่ยังมีช่องโหว่ ดู major #1
  • #4 migration ✅ ย้าย state.json เป็นอย่างสุดท้าย และใช้โฟลเดอร์เดิมต่อได้ ดู major #2 ประกอบ
  • #5 คำเตือน ✅ เปลี่ยนมาใช้ lastBuildAt (มีจุดที่ตั้งค่าผิดเล็กน้อย ดู nit #3)
  • #6 ยืนยันลบ ✅ ใช้ io.ask ตรง ๆ และรับ y/n เอง
  • #7 index.ts ✅ เพิ่ม event job.selected และ jobId แบบ optional
  • #8 path เก่า ✅ ลบข้อความเก่าและเพิ่มหัวข้อ README แล้ว

Findings ใหม่

major

1. SIGINT handler ปล่อย lock ไม่ทัน ทำให้ lock ค้างทุกครั้งที่กด Ctrl+C และถ้า Windows เอา pid ไปใช้ซ้ำ งานจะติด "กำลังรันอยู่" ถาวร

ทำไมสำคัญงานที่ติด lock จะเลือก r/d ไม่ได้ และ --resume ก็ข้ามงานนั้น spec ไม่มีทางให้ผู้ใช้ปลด lock เองเลย
หลักฐาน
  • handler ใน index.ts:47-53 ทำงานแบบ sync ทั้งหมดแล้วจบด้วย process.exit(130) แต่ spec ให้ unlock(id): Promise<void> ถูกเรียกใน handler นี้ ซึ่ง process จะ exit ก่อนที่ unlink จะเสร็จ ส่วนการปิดหน้าต่าง terminal (SIGHUP) ไม่ผ่าน handler และไม่ผ่าน finally เลย ผลคือ lock ค้างเป็นเรื่องปกติ ไม่ใช่กรณีพิเศษ
  • ระบบตัดสินว่า lock ค้างจาก process.kill(pid,0) อย่างเดียว ถ้า pid ถูก process อื่นเอาไปใช้ (ซึ่งเกิดบ่อยบน Windows) lock จะถูกมองว่ายังใช้อยู่ตลอด
แนวทางแก้ไข(ก) เพิ่ม unlockSync(id) ที่ใช้ fs.rmSync(..., {force:true}) สำหรับเรียกใน SIGINT handler และลงทะเบียน SIGHUP ด้วย handler เดียวกัน (ข) ให้ lock เก็บ {pid, startedAt} แล้วตอนแสดงเมนูและตอนปฏิเสธ r/d ให้บอก path ของ run.lock ว่า "ถ้าแน่ใจว่าไม่ได้รันอยู่ ให้ลบไฟล์นี้" เป็นทางออกขั้นต่ำ แล้วเขียนเทสต์ "SIGINT แล้วไม่มี run.lock เหลือ"
major

2. fallback ในขั้น 1 ของ migration ไม่มีวันถูกเรียกจากกรณีที่ตั้งใจไว้ แต่ถ้าเจอกรณีอื่นอาจทำให้โปรแกรมเริ่มไม่ได้เลย

ทำไมสำคัญspec ให้ throw ตอนย้ายไฟล์ไม่สำเร็จ ถ้า fallback ไม่เจอโฟลเดอร์ แล้วผู้ implement เลือก throw โปรแกรมจะพังทุกครั้งที่เริ่มรัน และ user จะเริ่มงานใหม่ไม่ได้เลย
หลักฐานเพราะย้าย state.json เป็นอย่างสุดท้าย ถ้าล้มครึ่งทาง state.json จะยังอยู่ที่ root เสมอ รอบถัดไปจึงได้ id เดิมจาก mtime และขั้น 2 (ใช้โฟลเดอร์ที่ไม่มี state.json ต่อ) ก็รับมือได้แล้ว กรณี "มี artifact ที่ root แต่ไม่มี state.json" จึงเกิดจากการย้ายไฟล์ล้มไม่ได้ จะเกิดได้ก็ต่อเมื่อ user ลบ state.json เอง ซึ่ง spec ไม่ได้บอกว่าถ้าไม่เจอโฟลเดอร์ที่ไม่มี state.json ต้องทำอะไร (ถ้าเจอหลายโฟลเดอร์ เช่นโฟลเดอร์จาก create() ที่ crash หลังเขียน lock ก็ไม่ได้บอกว่าจะเลือกอันไหน)
แนวทางแก้ไขให้เริ่มย้ายเฉพาะเมื่อมี state.json ที่ root และตัด fallback ในขั้น 1 ออก ถ้าเจอ artifact ค้างที่ root แต่ไม่มี state.json ให้บันทึก WARN แล้วปล่อยไว้ ไม่ throw
nit

3. lastBuildAt ถูกตั้งตั้งแต่ตอนเข้า BUILD และตอนคุยกับ PM ในเฟส BUILD ด้วย

ทำไมสำคัญคำเตือนจะขึ้นเกินจริงบ้าง แต่น้อยกว่ารอบแรกมาก
หลักฐานตอนกด confirm ใน REVIEW (design.ts runReview) ระบบตั้ง phase='BUILD' แล้ว save ทันที ซึ่งยังไม่มีการแก้โค้ดเลย นอกจากนี้ decide() ตอน escalate (io-util.ts:39) และการกด continue (build.ts:193) ก็ save ในเฟส BUILD ด้วย
แนวทางแก้ไขยอมรับได้ถ้าเขียนไว้ใน spec ถ้าต้องการให้แม่นขึ้น ให้ตั้งค่าเฉพาะเมื่อ Object.values(progress).some(p => p.rounds > 0) ซึ่งยังทำใน save ได้ ไม่ต้องแก้ build.ts
nit

4. ถ้า resume งาน legacy ที่คุยกับ PM ค้างไว้ ข้อความถัดไปที่ user พิมพ์จะกลายเป็น title

ทำไมสำคัญงานจะได้ชื่อไม่มีความหมาย เช่น "ต่อเลย" หรือ "โอเค"
หลักฐานเงื่อนไขที่ใช้คือ "ถ้า state.title ยังไม่มี" แต่งาน legacy ที่มี pmSessionId แล้ว จะขึ้นคำถาม "พิมพ์ข้อความถึง PM เพื่อคุยต่อ" (requirements.ts:9)
แนวทางแก้ไขตั้ง title เฉพาะเมื่อ !state.title && !state.pmSessionId
nit

5. เทสต์ initial state is saved when first ask throws จะพัง ถ้าใช้ load() ?? newState() โดยไม่ save

ทำไมสำคัญเทสต์นี้ไม่อยู่ในรายการที่ spec บอกให้ลบหรือแก้ ผู้ implement จะเจอเทสต์แดงโดยไม่รู้ว่าต้องทำยังไง
หลักฐานtests/orchestrator.test.ts:216-224 ใช้ MemoryStore ที่ว่างอยู่ และคาดว่า saves >= 1
แนวทางแก้ไขระบุใน spec ว่า if (!existing) await store.save(state) ต้องคงไว้
nit

6. race ของ lock และ jobId เมื่อมี 2 process ทำพร้อมกัน

ทำไมสำคัญมีโอกาสน้อย แต่ถ้าเกิด 2 process จะถือ lock เดียวกัน
หลักฐานตอนเจอ lock ค้าง ขั้นตอนคือ "อ่าน pid → เช็ก → เขียนทับ" ซึ่งไม่ได้ทำในจังหวะเดียว (ไม่ atomic) ถ้า 2 process เจอ lock ค้างพร้อมกัน ทั้งคู่จะเขียนทับและคิดว่าตัวเองได้ lock นอกจากนี้ create() ในวินาทีเดียวกันต้องใช้ mkdir แบบไม่ recursive (ให้ EEXIST ถ้ามีแล้ว แล้วค่อยลอง suffix ถัดไป) ถึงจะไม่ชนกัน และ process.kill ที่ได้ EPERM ต้องถือว่า process ยังอยู่
แนวทางแก้ไขตอนเจอ lock ค้าง ให้ unlink ก่อนแล้วลอง wx อีกครั้ง (ไม่ใช่เขียนทับ) ให้ create ใช้ mkdir ไม่ recursive และเขียนเรื่อง EPERM ไว้ในหัวข้อ Lock

สิ่งที่ไล่ตรวจแล้ว (ยืนยันว่าถูก)

  • ตั้ง lastBuildAt ใน save ได้จริงโดยไม่ต้องแก้ build.ts เพราะหลังรอบที่ worker แก้โค้ด ระบบ save ในเฟส BUILD เสมอ (build.ts:173/176)
  • การลบงานเปล่าอัตโนมัติไม่ไปลบงานที่อีก process เพิ่งสร้าง เพราะ create() เขียน lock ก่อน state.json และ list() ข้ามโฟลเดอร์ที่ยังไม่มี state
  • งานที่ user ขอแก้ตอน DELIVER แล้ววนกลับไป REQUIREMENTS ไม่ถูกนับเป็นงานเปล่า เพราะมี requirements อยู่แล้ว
  • ถ้า stdin ถูกปิด (EOF) หรือเกิด error ระหว่างรัน โปรแกรมจะผ่าน finally ซึ่งเรียก unlock แบบ async ได้ทัน เพราะไม่มี process.exit มาตัดก่อน
  • เทสต์ requirements.test.ts:42,105 ใช้ >= จึงยังผ่านแม้ save เพิ่ม 1 ครั้งจาก title

Verdict

fix-then-ship

findings รอบแรกแก้ครบแล้ว เหลือ SIGINT handler ที่ปล่อย lock แบบ async ไม่ทันก่อน exit และยังไม่มีทางให้ผู้ใช้ปลด lock เอง (#1) ซึ่งแก้ใน spec ได้ในไม่กี่บรรทัด ไม่ต้องรื้อ design
