เจตนา

ให้ Claude Code สั่ง agent-team ได้โดยไม่ต้องเปิด terminal แยก process รันค้างอยู่เบื้องหลัง ส่วนคำถามกับคำตอบส่งหากันผ่านไฟล์ในโฟลเดอร์ของงาน Claude รับคำถามแล้วถามผู้ใช้ต่อ

มีวิธีง่ายกว่านี้ไหม? ส่งผ่านไฟล์ถือว่าง่ายที่สุดแล้ว ถ้าเทียบกับ HTTP บน localhost หรือ named pipe และ Claude Code ก็เขียน stdin ของ process ที่รันเบื้องหลังไม่ได้อยู่แล้ว แต่ design ยังตัดของออกได้อีก คือ status --json ทำหน้าที่เดียวกับ wait --timeout 0 จึงควรใช้ implementation เดียวกัน

สิ่งที่ไล่แล้ว

  • ข้อความแรกผ่าน pendingPrompt ใช้ได้จริง: src/phases/requirements.ts:31 ใช้ state.pendingPrompt ?? askNonEmpty(...) และตั้ง title ที่บรรทัด 34-37 จึงไม่ต้องแก้ phase
  • การ resume ไม่ถามอะไร: resumeLatest (src/job-menu.ts) เลือกงานแรกที่ lock ได้โดยไม่เรียก io.ask จึงใช้ในโหมด headless ได้ ส่วน --job <id> ยังต้องเขียนเพิ่ม
  • จุดที่ถามผู้ใช้ทั้งหมด: ทุกจุดใน phase ผ่าน ask/chooseOrText (io-util.ts, requirements.ts:59,75,81,86, design.ts, deliver.ts, build.ts:240) ไม่มีจุดไหนใช้ stdin ตรง ๆ

Findings

MAJORบน Windows ถ้า kill task เบื้องหลัง node ลูกอาจค้างอยู่ รอคำตอบไปตลอดและถือ lock ไว้

ทำไมถึงสำคัญ
agent-team ที่ได้จาก npm link เป็น shim ที่ไปเปิด node อีกทีผ่าน bin/agent-team.mjs ถ้า Claude Code หยุด task หรือปิด session ไป process ลูกอาจไม่ตายตาม HeadlessIO จะวนเช็กไฟล์ไปเรื่อย ๆ และงานนั้นก็ถูก lock ไว้ตลอด ทำให้ --resume ข้ามงานนี้ไป
หลักฐาน
design ไม่มีทั้งคำสั่งหยุดและ timeout ตอนรอคำตอบ ส่วน makeInterruptHandler (src/interrupt.ts) รับแค่ SIGINT/SIGHUP และ resumeLatest ข้ามงานที่มี lock
แนวทางแก้ไข
(1) เพิ่ม agent-team stop [--job] ที่เขียนไฟล์ stop ให้ HeadlessIO เห็นตอน poll แล้วเรียก interrupt handler เดิม ถ้า process ไม่ตอบภายในไม่กี่วินาทีค่อย process.kill(lock.pid) (2) ใส่ idle timeout ตอนรอคำตอบ เช่น 2 ชม. ตั้งค่าใน config ได้ ครบเวลาแล้วให้ปลด lock แล้วจบแบบ resume ต่อได้

MAJORถ้าอ่านไฟล์ระหว่างที่อีกฝั่งยังเขียนไม่เสร็จ จะ parse ไม่ผ่าน หรือคำตอบหาย

ทำไมถึงสำคัญ
answer กับ HeadlessIO เป็นคนละ process กัน ถ้า JSON.parse เจอไฟล์ที่เขียนไปครึ่งเดียวแล้วโยน error ออกมาจาก ask ทั้ง run จะล้ม อีกกรณีคือเรียก answer สองครั้งก่อนที่ process จะอ่าน คำตอบแรกจะหายไปเฉย ๆ
หลักฐาน
design บอกแค่ว่า "เขียนไฟล์" กับ "poll" ไม่ได้ระบุว่าต้องเขียนแบบ atomic หรือทำอะไรเมื่อ parse ไม่ผ่าน
แนวทางแก้ไข
ทุกไฟล์ให้เขียนลงไฟล์ชั่วคราวก่อนแล้วค่อย rename ฝั่งอ่านถ้าเจอ JSON พังให้ข้ามรอบนั้นไปรอรอบถัดไป answer ต้องปฏิเสธถ้ามี answer.json ค้างอยู่แล้ว หรือถ้า lock ตายไปแล้ว ตอน process เริ่มให้ลบ question.json/answer.json ที่ค้างมาจากรอบก่อน

MAJORindex.ts สร้าง CliIO ทุกครั้ง ถ้าใช้ในโหมด headless readline จะผูกกับ stdin ของ task เบื้องหลัง

ทำไมถึงสำคัญ
new CliIO() ที่ต้นของ main() เปิด readline บน stdin และส่ง cli.status (Spinner) ให้ runner ใน task เบื้องหลัง stdin มักปิดอยู่ จึงอาจเกิด close/EOF (EOF_MESSAGE) และ Spinner จะเขียน escape code ลง output ของ task ดังนั้นคำพูดใน design ที่ว่า "orchestrator/phase ไม่ต้องแก้" ถูก แต่ index.ts ต้องแยกทางกันจริง
หลักฐาน
src/index.ts:19 (สร้าง CliIO), src/index.ts:84-92 (ส่ง cli.status ให้ runner), src/cli.ts:61-66 (close → reject EOF)
แนวทางแก้ไข
ให้ plan แยก main() เป็น runInteractive/runHeadless โดยฝั่ง headless ไม่สร้าง CliIO เลย ใช้ LoggingIO(new HeadlessIO(...)) เพื่อให้ agent-team logs ยังเห็นทุกอย่าง และให้ status sink เป็นตัวที่บันทึก activity ล่าสุด

MAJORถ้าวาง SKILL.md ที่ skills/agent-team/ จะไปอยู่ใน plugin team ของ role agent

ทำไมถึงสำคัญ
ใน repo โฟลเดอร์ skills/ เป็น plugin ที่ role agent โหลดไปใช้อยู่แล้ว skill สำหรับ Claude Code ของผู้ใช้เป็นคนละกลุ่มกัน ถ้าวางปนกัน วันหนึ่งอาจมีคนเปิดให้ role เห็นคำสั่ง agent-team run ซึ่งจะไปรันซ้อนตัวเองและเสียเงิน อีกทั้งยังทำให้โครงสร้างสับสน
หลักฐาน
skills/README.md ("โฟลเดอร์นี้เป็น plugin ชื่อ team") และ package.json files ที่มี skills
แนวทางแก้ไข
ย้ายไปไว้ที่ claude-skill/agent-team/SKILL.md (เพิ่มเข้า files ด้วย) แล้วให้ install-skill copy จากตรงนั้น

MAJORwait --timeout 600 ชนกับ timeout ของ Bash tool ใน Claude Code

ทำไมถึงสำคัญ
Bash tool ตั้ง timeout ค่าเริ่มต้นไว้ 120s และสูงสุดได้ 600s ถ้าใช้ wait ตามค่าเริ่มต้น tool จะตัดคำสั่งทิ้งก่อน Claude จะไม่ได้ JSON กลับมา และช่วง BUILD ใช้เวลาเกิน 10 นาทีบ่อย
หลักฐาน
ข้อจำกัดของ Bash tool (ค่าเริ่มต้น 120000ms สูงสุด 600000ms)
แนวทางแก้ไข
ให้ค่าเริ่มต้นของ wait เป็น 540s แล้วเขียนใน SKILL.md ว่าต้องเรียกด้วย Bash timeout: 600000 และถ้าได้ timeout กลับมาให้เรียก wait ซ้ำพร้อมรายงานความคืบหน้าสั้น ๆ

NITช่วงของ messages ยังไม่ชัด ถ้าเรียกซ้ำหลัง timeout จะได้ข้อความเดิมซ้ำ

ทำไมถึงสำคัญ
"say ตั้งแต่คำตอบก่อน" จะคืนก้อนเดิมทุกครั้งที่ wait timeout แล้วถูกเรียกใหม่
แนวทางแก้ไข
ให้ wait --since <seq> คืนค่า lastSeq กลับมา และให้ SKILL.md ส่งค่านี้ต่อไปทุกครั้งที่เรียก

NITถ้าไม่ใส่ --job ระบบจะใช้งานล่าสุด ซึ่งเสี่ยงส่งคำตอบผิดงาน

ทำไมถึงสำคัญ
ถ้ามีงาน headless 2 งานในโปรเจกต์เดียว answer อาจไปลงงานที่ไม่ได้ตั้งใจ
แนวทางแก้ไข
ให้ SKILL.md ส่ง --job ทุกครั้ง (ใช้ jobId ที่ run พิมพ์) ถ้าไม่ใส่ ให้ใช้งานที่มีคำถามรออยู่งานเดียว ถ้ามีมากกว่า 1 งานให้ error พร้อมแสดงรายชื่อ

NITตอนงานรันยาว Claude มองไม่เห็นว่ากำลังทำอะไรอยู่

ทำไมถึงสำคัญ
ข้อมูลจาก status.update(describeToolUse(...)) (src/runner.ts:225) ใน design นี้จะหายไปหมด ผู้ใช้ถามว่า "ถึงไหนแล้ว" Claude ก็ตอบได้แค่ชื่อ phase
แนวทางแก้ไข
ให้ status sink ใน headless เขียน activity ล่าสุด (role + tool) ลงไฟล์ แล้วใส่ไว้ใน JSON ของ wait/status

คำตัดสิน

fix-then-ship  แนวทางโดยรวมถูกแล้ว แต่ต้องใส่ stop/idle timeout, การเขียนไฟล์แบบ atomic, การแยก index.ts, ที่วาง SKILL.md และ timeout ของ wait ลงใน design ก่อนเขียน plan
