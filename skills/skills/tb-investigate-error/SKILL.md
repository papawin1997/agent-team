# Investigate Error → รายงาน HTML

เป้าหมายของ skill นี้คือ **อธิบายให้ผู้ใช้เข้าใจว่า error เกิดขึ้นได้ยังไง** แล้วส่งมอบเป็น
รายงาน HTML ภาษาไทยที่เปิดอ่านสบายตา ไม่ใช่การรีบกระโจนไปแก้โค้ด ผู้ใช้กำลังพยายามสร้าง
mental model ของบั๊ก — งานของเราคือไล่โค้ดจริงให้เห็น แล้วเล่าให้ฟังอย่างซื่อสัตย์ว่าจุดไหนพัง
ทำไม และอะไรเกี่ยวข้องบ้าง

## ลำดับการทำงาน

### 1. เริ่มด้วยวินัย debug-mantra
skill นี้ต่อยอดจาก `debug-mantra` ให้เรียกใช้วินัย 4 ข้อนั้นเป็นกรอบคิดก่อน:
reproduce → know the fail path → falsify hypothesis → every run is a breadcrumb
ถ้า skill `debug-mantra` มีอยู่ในระบบ ให้ invoke มันด้วยเพื่อท่อง mantra และจัดระเบียบการสืบสวน
หัวใจที่ห้ามลืม: **ถ้า reproduce ไม่ได้หรือข้อมูลไม่พอ ให้บอกตรง ๆ อย่าเดามั่ว** — เขียนใน
รายงานว่าอะไรที่ยังพิสูจน์ไม่ได้ และต้องการ artifact อะไรเพิ่ม

### 2. ไล่หาจุดพัง (fail path) จากของจริงในโค้ด
อย่าวิเคราะห์จากความจำหรือการเดา ต้องเปิดโค้ดจริงเสมอ:

- **เกาะ error string เป็นจุดเริ่ม** — grep ข้อความ error ที่ผู้ใช้ให้มา (ตัดส่วน dynamic
  เช่นชื่อ column/ค่าออก เหลือ literal ที่อยู่ในซอร์ส) เพื่อหา func ต้นทาง
  เช่น `grep -rn "Failed to create ... record" --include="*.go"`
- **ไล่ trace ลงไปตาม layer** ของ codebase นี้: `handler → service → usecase → repository → entity`
  อ่าน func ที่เกี่ยวข้องจริง ดูว่าค่าถูกประกอบ/แปลง/ดึงมายังไง จนถึงจุดที่ DB/ระบบ reject
- **enumerate "ปุ่ม" ที่มีผลต่อผลลัพธ์** — เงื่อนไข branch, ค่าที่อาจเป็น nil/NULL, schema
  constraint (เช่น `gorm:"not null"`), default ของ struct, ลำดับ query ที่ไม่มี OrderBy ฯลฯ
  จุดที่ "ต้นทาง nullable แต่ปลายทาง not null" หรือ "len==0 แล้วใช้ index [0]" คือ pattern
  คลาสสิกของบั๊กแบบนี้
- เก็บทุกอย่างที่อ้างเป็น **`file:line`** ไว้ใส่รายงาน (path คลิกได้)

### 3. ตั้งสมมติฐานแล้วพยายาม "หักล้าง" ก่อน
สร้างสมมติฐาน 3–5 อันเรียงตามความน่าจะเป็น อย่ายึดอันแรกที่ดูเข้าท่า สำหรับแต่ละอันให้คิดว่า
**"การทดลองอะไรที่จะพิสูจน์/ล้มมันได้เร็วที่สุด"** เช่น SQL query เช็คข้อมูลจริง, log ที่ต้องดู,
หรือค่าที่ต้องตรวจ แล้วเขียนวิธียืนยันนั้นลงในรายงานเสมอ — เพราะผู้ใช้จะได้เอาไปกดต่อเองได้

### 4. ยืนยันสมมติฐานก่อนสร้าง HTML

**ห้ามสร้างหรืออัปเดตไฟล์ HTML จนกว่าจะยืนยันสาเหตุจากหลักฐานจริงแล้ว**

ถ้ายังต้องการ query/ข้อมูลเพิ่มเติม (เช่น SQL ตรวจ DB, log, ค่าจากระบบ) ให้:
1. **ถามใน conversation** — แสดง query/คำสั่งที่ต้องรัน แล้วรอผู้ใช้วางผลลัพธ์กลับมา
2. **รอผลลัพธ์** — อย่าอัปเดต HTML ด้วยสมมติฐาน ต้องมีหลักฐานยืนยันก่อน
3. **เมื่อยืนยันแล้วค่อยสร้าง HTML** ครั้งเดียวด้วยข้อมูลครบถ้วน

ตัวอย่างที่ถูก:
> "ก่อนจะสรุปได้ ขอให้รัน query นี้ใน DB แล้วส่งผลลัพธ์มาให้ดูก่อน:
> `SELECT user_id, is_primary FROM dbo.employment_details WHERE user_id = '12345'`"

ตัวอย่างที่ผิด: สร้าง HTML ไปก่อน แล้วค่อยอัปเดตทีหลังเมื่อมีข้อมูลเพิ่ม

### 5. ออกรายงาน HTML
ใช้ template สำเร็จที่ `assets/report_template.html` (มี CSS theme + โครง 3 หัวข้อให้แล้ว
ห้ามเขียน CSS ใหม่ — เติมแค่เนื้อหาในจุด `<!-- FILL ... -->` และแทน `__TITLE__` ฯลฯ)
อ่านคอมเมนต์หัวไฟล์ template เพื่อดู class ที่ใช้ได้ (`.pill file`, `.step fail`, `.nil`, ...)

**เนื้อหาบังคับของรายงาน:**
1. **พังที่ไหน** — func + `file:line` + อธิบายการทำงานของ func นั้น แปะโค้ดจุดพังใน `<pre>` ได้
2. **ทำไม / ข้อมูลอะไรผิด** — ต้นเหตุ + ระบุค่า/field ที่ผิด + **สมมติฐานจัดอันดับพร้อมวิธียืนยัน**
3. **flow ที่เกี่ยวข้อง** — ไล่ตั้งแต่ entry (route/handler) ถึง DB เป็น step ใส่ `file:line` ทุกขั้น
   และทำเครื่องหมายขั้นที่พัง (`class="step fail"`)
- อ้าง `file:line` ทุกครั้งที่พูดถึงโค้ด ไม่อ้างลอย ๆ
- ปิดท้ายด้วยสรุปสั้น + คำสั่ง/วิธียืนยันที่เร็วที่สุด
- ถ้าผู้ใช้ไม่ได้ให้ payload/request ก็ข้ามส่วนที่เกี่ยวกับ input ได้ ไม่ต้องเดาขึ้นมา

### 6. เซฟไฟล์ + เปิดอัตโนมัติ
ไฟล์ต้องไปอยู่ที่ `docs/error/` ใต้ **root ของ project** (ไม่ใช่ cwd ที่อาจอยู่ลึก):

```bash
ROOT=$(git rev-parse --show-toplevel)
mkdir -p "$ROOT/docs/error"
# เซฟไฟล์เป็น docs/error/<ชื่อสื่อความหมาย>.html เช่น terminate-is-primary-null.html
open "$ROOT/docs/error/<ชื่อไฟล์>.html"
```

ตั้งชื่อไฟล์ให้สื่อความหมายจากตัว error (kebab-case) เช่น `terminate-is-primary-null.html`,
`payment-nil-pointer-getterminate.html` — เพื่อให้เปิดหา/อ้างอิงย้อนหลังได้ง่าย
ถ้าไม่ได้อยู่ใน git repo ให้ถามผู้ใช้ว่าจะวางไฟล์ไว้ที่ไหน อย่าเดา path เอง

## ขอบเขต
- skill นี้ทำ **การวิเคราะห์สาเหตุ** เท่านั้น ไม่แก้โค้ดในขั้นตอนนี้ ปิดท้ายรายงานด้วยการเสนอว่า
  ถ้าต้องการแนวทางแก้ที่กระทบน้อยที่สุดให้แจ้งได้
- ถ้าหลักฐานไม่พอจะสรุปสาเหตุได้แน่ชัด ให้ระบุในรายงานว่ายังเป็นสมมติฐาน และต้องเก็บอะไรเพิ่ม
  เพื่อยืนยัน — ความซื่อสัตย์ต่อสิ่งที่พิสูจน์ได้สำคัญกว่าการฟันธงสวย ๆ
