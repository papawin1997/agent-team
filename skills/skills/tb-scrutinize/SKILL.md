# ตรวจสอบโค้ด (Scrutinize)

มองจากภายนอกว่าสิ่งนี้ควรมีอยู่หรือไม่ แล้วตรวจสอบว่าทำได้จริงตามที่อ้าง end-to-end

## จุดยืน

- **คนนอก.** ลืมว่าใครเขียนและทำไมถึงคิดว่าถูก อ่านโค้ดใหม่ตั้งแต่ต้นเหมือนไม่เคยเห็นมาก่อน
- **ดูทั้งเส้นทาง ไม่ใช่แค่บรรทัดที่แก้.** บรรทัดที่แก้ (diff) เป็นแค่จุดเริ่ม ต้องไล่ตามว่าโค้ดถูกเรียกต่อกันเป็นทอด ๆ ไปถึงไหน
- **บอกให้แก้ได้จริง กระชับ มีเหตุผล.** ทุกสิ่งที่เจอ (finding) ต้องบอก *จะแก้ยังไง*, *ทำไมต้องแก้*, และ *หลักฐาน* ที่ทำให้สรุปแบบนั้น

## ขั้นตอน

ทำตามลำดับ ห้ามข้าม

### 1. เจตนา — สิ่งที่ต้องการทำคืออะไร

- สรุปเป้าหมายในประโยคเดียว ด้วยคำพูดของตัวเอง ถ้าทำไม่ได้ แปลว่า artifact ไม่ชัดเจน — บอกและหยุด
- ถาม: **มีวิธีที่ง่ายกว่า เล็กกว่า หรือเรียบร้อยกว่าที่จะได้ผลเหมือนกันไหม?** ลองคิดถึง:
  - ไม่ต้องทำเลย (ปัญหานี้มีอยู่จริงหรือเปล่า?)
  - ใช้ของที่มีอยู่แล้วในโปรเจกต์ แทนที่จะเขียนของใหม่เพิ่ม
  - แก้แบบเล็กกว่าที่แก้ปัญหาได้ 90% โดยเสี่ยงแค่ 10%
  - ไปแก้ที่จุดอื่นแทน (เช่น แก้ที่ค่า config แทนการแก้โค้ด, แก้ที่ตอน build แทนตอน run)
- ถ้ามีทางที่ดีกว่า บอกให้ชัดพร้อมเหตุผล นี่คือสิ่งที่มีค่าที่สุดที่ควรพูด — บอกก่อนจะไปไล่รีวิวทีละบรรทัด

### 2. ติดตาม — เดิน code path จริง

- สำหรับแต่ละสิ่งที่การแก้นี้อ้างว่าทำได้ ให้ไล่เส้นทางตั้งแต่ต้นจนจบในโค้ดจริง ไม่ใช่ดูแค่บรรทัดที่แก้:
  - จุดเริ่ม (ใครเรียกฟังก์ชันนี้) → เรียกต่อไปที่ไหนบ้าง → เข้าเงื่อนไข if/else ทางไหน → ไปแก้ตัวแปร/ข้อมูลตรงไหน → จบที่ผลลัพธ์ (return) หรือผลข้างเคียงอะไร
  - ดูโค้ดที่ *ไม่ได้แก้* ที่อยู่ก่อนและหลังบรรทัดที่แก้ด้วย บั๊กมักซ่อนอยู่ตรงรอยต่อระหว่างของเก่ากับของใหม่
- ถ้าเป็น plan หรือเอกสารออกแบบ: ลองวางขั้นตอนที่เสนอทาบกับระบบจริงที่มีอยู่ มันไปต่อกับของจริงตรงไหน มีข้อไหนที่คิดเอาเองว่าจริงแต่ยังไม่จริง?
- จดทุกจุดที่ไล่โค้ดแล้ว "เอ๊ะ" (เช่น เข้า if ทางที่ไม่คาดคิด, โค้ดที่ไม่มีวันถูกเรียก, ตัวแปร/ข้อมูลที่ไม่รู้ว่ามีอยู่) ความรู้สึกแปลก ๆ คือสัญญาณว่ามีอะไรผิด

### 3. ตรวจสอบ — ทำได้จริงตามที่อ้างไหม

สำหรับแต่ละ claim ที่ change/plan ทำ ตอบ:

- **เส้นทางโค้ดที่ไล่มา ทำให้เกิดผลแบบนั้นจริงไหม?** เขียนให้เห็นชัด เช่น "อ้างว่าทำ X ได้ เส้นทาง: A → B → C พอถึง C เห็นว่า [...] ดังนั้น [จริง/ไม่จริง]"
- **ใส่ข้อมูล/อยู่ในสถานะแบบไหนแล้วจะพัง?** เช่น กรณีสุดขอบ (edge case), มีคนเรียกพร้อมกันหลายคน, เส้นทางที่เกิด error, ทำสำเร็จครึ่งเดียวแล้วพัง, ระบบ retry ซ้ำ, ค่าว่าง/null/ภาษาไทย-อีโมจิ/ข้อมูลก้อนใหญ่มาก, โค้ดเดาว่าข้อมูลจะมาตามลำดับ
- **มันแอบเปลี่ยนอะไรโดยไม่บอกหรือเปล่า?** เช่น ความเร็ว, ความหมายของ error ที่เปลี่ยนไป, log/การมองเห็นปัญหา, สัญญา (input/output) ที่โค้ดอื่นเรียกใช้อยู่, รูปแบบไฟล์ที่บันทึกลงดิสก์หรือข้อมูลที่ส่งผ่าน network
- **เทสครอบคลุมแค่ไหน?** เทสได้ทดสอบเส้นทางที่เราไล่มาจริงไหม หรือผ่านแบบข้าม ๆ (เช่น mock จนไม่ได้ทดสอบของจริง, เช็คแค่ค่ากลางทาง, ทดสอบแค่กรณีที่ทุกอย่างปกติ)

### 4. รายงาน

แสดงผลทีละข้อที่เจอ (finding) เรียงตามความรุนแรง (blocker = ของตาย ต้องแก้ก่อน → major = เรื่องใหญ่ → nit = เรื่องเล็กจุกจิก) แต่ละข้อบอก:

- **สิ่งที่เจอ (Finding)** — หนึ่งประโยค เจาะจง อ้าง `file:line` (ชื่อไฟล์:เลขบรรทัด) เมื่อทำได้
- **ทำไมถึงสำคัญ** — บอกผลที่จะตามมาจริง ๆ ไม่ใช่ท่องหลักการลอย ๆ
- **หลักฐาน** — ขั้นตอนการไล่โค้ด หรือข้อมูล input ที่ทำให้เห็นปัญหา
- **แนวทางแก้ไข** — แก้ยังไงให้ชัดและเล็กที่สุด

ปิดท้ายด้วยคำตัดสินหนึ่งบรรทัด: ship (ส่งได้) / fix-then-ship (แก้แล้วค่อยส่ง) / rework (รื้อทำใหม่) / reject (ตีกลับ) — พร้อมเหตุผลข้อใหญ่ที่สุดหนึ่งข้อ

จากนั้น **บันทึก HTML report** ตาม spec ด้านล่าง

## กฎการทำงาน

- **ห้ามผ่านให้แบบขอไปที.** ตอบแค่ "LGTM" (ดูดีแล้ว) ใช้ไม่ได้ ถ้าไม่เจออะไรจริง ๆ ให้บอกว่าไล่โค้ดส่วนไหนและตรวจอะไรไปบ้าง เพื่อให้ผู้ใช้ตัดสินได้ว่ารีวิวครอบคลุมส่วนสำคัญหรือยัง
- **ไม่อ้างหลักฐาน ถือว่าไม่เกิดขึ้น.** ทุกอย่างที่พูดถึงโค้ด ต้องอ้างเส้นทาง, ไฟล์, หรือบรรทัดให้ชัด ห้ามพูดลอย ๆ แบบ "อาจพังตอนคนใช้เยอะ"
- **แยกสิ่งที่ "เขาอ้าง" ออกจากสิ่งที่ "เราตรวจแล้ว".** "PR บอกว่าทำ X ได้" กับ "ผมไล่โค้ด X แล้ว ยืนยัน/พบว่าไม่จริง" คนละเรื่องกัน — เขียนแยกกันให้ชัด
- **ต้องถามเรื่อง "มีวิธีง่ายกว่าไหม" เสมออย่างน้อยหนึ่งครั้ง.** ต่อให้แก้นิดเดียวก็ตาม เว้นแต่ผู้ใช้บอกว่า "ไม่ต้องตั้งคำถามเรื่องขอบเขตงาน"
- **ถ้ามีปัญหาเชิงโครงสร้าง อย่าเอาเรื่องเล็กมาถ่วง.** ถ้าขั้นตอนที่ 1 หรือ 2 เจอปัญหาจริง ให้พูดเรื่องนั้นก่อน ส่วนเรื่องจุกจิก (nit) เลื่อนไปท้ายหรือตัดทิ้ง
- **ห้ามยกยอ ห้ามอ้อมค้อม.** "PR ดีมากเลยแต่..." ไม่มีประโยชน์ บอกสิ่งที่เจอตรง ๆ

## การบันทึก HTML Report

หลัง output ผลใน chat แล้ว ให้บันทึก HTML report ทุกครั้ง:

**โฟลเดอร์:** `docs/check/` (ใต้ root ของโปรเจกต์ที่กำลัง review)

**ชื่อไฟล์:** `YYYY-MM-DD-<topic>-tb-scrutinize.html`

**รูปแบบ HTML:** สร้าง HTML ที่อ่านง่าย ครอบคลุม:
- หัวข้อ: ชื่อ artifact ที่ review + วันที่
- เจตนา: สรุป 1-2 ประโยค
- Findings: แสดงเป็น card แยกตาม severity (blocker = แดง, major = ส้ม, nit = เทา) แต่ละ card มี finding, ทำไมสำคัญ, หลักฐาน, แนวทางแก้ไข
- Verdict: แสดง badge สีชัดเจน (ship = เขียว, fix-then-ship = เหลือง, rework = ส้ม, reject = แดง)

เปิด HTML หลังสร้างเสร็จ ด้วยคำสั่งที่ตรงกับ OS:

- **macOS** → `open docs/check/<filename>.html`
- **Windows** → `start docs/check/<filename>.html`
- **Linux** → `xdg-open docs/check/<filename>.html`

## ตัวอย่าง (สำหรับมือใหม่)

สมมติมีคนส่ง PR มาให้รีวิว: *"เพิ่ม cache ให้ฟังก์ชัน `getUser(id)` เพื่อให้เร็วขึ้น"* โค้ดที่แก้คือ

```js
function getUser(id) {
  if (cache[id]) return cache[id];      // บรรทัดที่เพิ่มเข้ามา
  const user = db.queryUser(id);
  cache[id] = user;                     // บรรทัดที่เพิ่มเข้ามา
  return user;
}
```

เดินตาม 4 ขั้นตอนแบบนี้:

**1. เจตนา** — เป้าหมาย: ทำให้ `getUser` เร็วขึ้นด้วยการจำผลลัพธ์ไว้ (cache)
มีวิธีง่ายกว่าไหม? → ถ้าข้อมูล user เปลี่ยนบ่อย การ cache อาจสร้างปัญหามากกว่าได้ประโยชน์ ลองถามก่อนว่า "ช้าจริงไหม วัดมาหรือยัง"

**2. ติดตาม** — ไล่เส้นทาง: ใครเรียก `getUser` บ้าง → พบว่ามีหน้าโปรไฟล์เรียกหลังผู้ใช้ "แก้ไขชื่อ" → ตรงนี้แหละที่ "เอ๊ะ"

**3. ตรวจสอบ** — ใส่ข้อมูลแบบไหนแล้วพัง?
- ผู้ใช้แก้ชื่อ → `db` อัปเดตแล้ว แต่ `cache[id]` ยังเป็นชื่อเก่า → ฟังก์ชันคืนค่าเก่า (นี่คือบั๊ก data เก่าค้างใน cache)
- ถ้า `db.queryUser(id)` คืน `null` (ไม่เจอ user) → `cache[id] = null` แล้วรอบหน้า `if (cache[id])` เป็น false เลย query ซ้ำทุกครั้ง → cache ไม่ทำงานสำหรับ user ที่ไม่มี

**4. รายงาน**

- **สิ่งที่เจอ** — cache ไม่ถูกล้างเมื่อข้อมูล user เปลี่ยน (`user.js:2`) ทำให้คืนค่าชื่อเก่า
  **ทำไมถึงสำคัญ** — ผู้ใช้แก้ชื่อแล้วเห็นชื่อเก่า เหมือนระบบไม่บันทึก
  **หลักฐาน** — เส้นทาง: หน้าแก้ชื่อ → `db` อัปเดต → แต่ `cache[id]` ไม่ถูกอัปเดต → `getUser` คืนค่าจาก cache เดิม
  **แนวทางแก้ไข** — ลบ `cache[id]` ตอนที่อัปเดต user (เพิ่ม `delete cache[id]` ในฟังก์ชันแก้ไขข้อมูล)

คำตัดสิน: **fix-then-ship (แก้แล้วค่อยส่ง)** — เหตุผลใหญ่สุด: ยังมีบั๊ก cache ค้างค่าเก่า
